## 0. The one finding that changes everything else

**Saved events are not durable on the live link.** The production store falls back to a file in each function
instance's temp folder (`src/domain/store/index.ts:36-39`: no `DATABASE_URL`, no `BLOB_READ_WRITE_TOKEN`, so
`FileStore(os.tmpdir())`). Measured at 13:14 EDT:
- `GET /api/w/audit-gap1/state?role=priya` ten times in a row: six responses carried 6 events, four carried 0
  (different `x-vercel-id` per response).
- Six renders of `/w/audit-gap1/daniel` after six events were saved: all six said "Nothing recorded in this workspace
  yet" and "v3, none of our changes applied yet".
- `audit-gap2`: Jo moved the clock to 2028-02-01 (seq 3 accepted); six later GETs all returned `storyAt
  2026-06-23T06:05`.
The decision log already names this ("Storage still per-instance temp until Neon is added", 17 Oct 12:03). It means
the grader walk step 5 ("Reload: the adjustment is still there") and every cross-role check fail at random, roughly
four times in ten. It also blocked several of my own verifications below (marked "blocked by store").
Fix is S to M: provision Postgres (adapter exists) or set a Blob token (adapter exists, weaker ordering). Nothing in
the round G plan matters to a grader more than this.

## 3. Notification slice (notify.ts, Bell.tsx) against H3 B and C

Correctness, with evidence:
- Tests pass: `vitest run tests/unit/notify.test.ts tests/unit/policy.test.ts tests/unit/checks/ledger.test.ts` 62/62
  at 13:13 EDT. Bell renders live for staff and clients, absent for the examiner (page greps).
- Partner-threshold effect is measured against v3's value, not the claim's current value (`notify.ts:59` uses
  `ix.line(latest).value`). A second adjustment on the same line reports the wrong effect. Use `state.claims[id].current`
  (notify.ts does not receive `state`; pass it, see architecture).
- Staleness is re-derived in notify.ts (`signers` map, lines 36, 54, 70) separately from `project.ts` (`SignOff.stale`).
  Two sources of truth for one rule; they will drift (undo of a sign-off, bulk groups).
- `answer_recorded` always goes to the preparer seat (line 79), not to whoever asked (Marcus asks, Priya is told).
  Resolve the asker from `payload.questionSeq`.
- `review_note` goes to the preparer only (line 46). H3 B says addressee and preparer. There is no addressee field on a
  review note in `DrawerActions`; either add `to` or send to the author of the claim's last adjustment as well.
- Applied adjustment notifies the preparer seat (line 53) but not the proposer when they differ (Marcus proposes, Daniel
  applies, Marcus hears nothing).
- Rules in H3 B with no implementation: e-file rejection to preparer, reviewer and both clients in plain words; client
  approval requested to both spouses; approval requested to Helen (no such event exists; the threshold path covers one
  case); deadline warning to assignee and Jo; bulk actions as one grouped notice (a bulk sign-off today produces no
  notice at all); clock moved ("an event everyone sees", H3 A) is silent.
- Also silent: `finding_cleared`, `decision`, `verification`, `attach_note`, `workspace_reset`. Decide each; "cleared a
  finding on X" is one the reviewer and partner would expect.
- Marcus wording: claim labels pass through `maskText` (line 41), fine; no notice text carries free text, so no
  identifiers can leak (test covers it). The H3 phrase "an identifier was corrected" is not needed while labels are the
  only text.
- Bell href for a client with a `claimId` drops the claim (Shell.tsx:89) and lands on Home, which today shows no
  question list; fix together with gap 2.
- Toast shows only the newest arrival when several land in one poll (Bell.tsx:27); acceptable, say so in a comment.
- Read state is per browser (`localStorage` key `wp.read.<ws>.<role>`), not per person on the server. The round G plan
  names the trade-off; acceptable for the demo. The same key should drive "since you last looked".
- H3 C "Today / Earlier" grouping is absent. Low.
- `notify.ts:32` prefers the literal `'priya'` among preparer seats. The seat is already the assigned preparer; drop the
  literal and take `assignment_at_start.preparer` through `policy`.

Architecture (the things that would otherwise be patched one at a time):
- **One rule table, two sources.** Round G adds packet-story notices (rejection, deadlines, late messages). Keep a single
  table: `source` (event type or story kind) to recipients function and wording per audience (staff, client), with
  masking applied once at the end. Do not add a second `switch` for story sources.
- **Notice identity must stop being `seq`.** `BellItem.seq`, the read set `Set<number>`, the toast's `newest` max and
  the e2e all key on an event seq. Story-derived notices have no seq. Define `Notice { id: string; at: string; ... }`
  now (`ev:<seq>`, `story:<tl-id>`, `deadline:<date>`), sort by `at`, keep read state as a set of ids. Doing this
  before adding story sources avoids rewriting Bell twice.
- **Pass the projection, not raw events.** `notificationsFor(ix, state, role)`: staleness, current values, the clock and
  the role filter already live in `WorkspaceState`; notify.ts should consume them, not recompute them.
- **Since-you-last-looked is the same projection** with a cut-off; build it as a filter on notices, not a new list.
