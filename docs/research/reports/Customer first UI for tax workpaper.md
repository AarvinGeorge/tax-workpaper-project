# Anchor every number to its proof

A tax workpaper that a 20-year CPA trusts and a new hire can use on day one comes down to two things: put every number next to its source, and make review state impossible to misread. Software for this already exists in two separate groups, and neither has both halves. Tax and audit incumbents (SurePrep SPbinder, Caseware Cloud, UltraTax CS) have role-levelled sign-offs with names and timestamps, and they **warn** when a signed-off document changes. **None of the products I could document actually revokes the stale sign-off.** "Send back" sits in practice-management tools as a pipeline move, apart from the notes that explain why the work was sent back. AI-native and developer tools solve the other half. Claude, Hebbia and Linear drive a right-hand panel from whatever is selected in the centre. DataSnipper links each value to a box on its source document. GitHub turns review into gates: stale approvals are dismissed, every conversation must be resolved, checks must pass, and the last person to change something cannot approve it. The opportunity is to combine the two: a three-pane workpaper where a click on any number opens its highlighted source on the right, and sign-off becomes a gate scoped to individual values that reopens itself when an input changes. Usability research (Nielsen's heuristics, NN/g on progressive disclosure, Google PAIR on trust) supports serving novices and experts with **one layered screen rather than two modes**: a recognisable default, shortcuts on top, two levels of disclosure at most, and categorical confidence tied to an action, not a percentage. The evidence for practitioner pain is thinner than expected. Several AI-native tax tools document their review stage poorly in public. Where this report goes beyond the sources, it says so.

## Incumbents flag stale sign-offs but leave them standing

Review in today's tax software uses fixed role levels. SurePrep SPbinder has four, L1 Preparer, L2 Reviewer, L3 Signer and L4 Partner. Each sign-off logs name, date and time, and in the Review Tree a signed-off workpaper turns green and the unreviewed count drops by one ([SPbinder: Sign off documents](https://www.thomsonreuters.com/en-us/help/sureprep/spbinder/work-with-documents/sign-off-documents.html)). When a workpaper changes after sign-off, **"A Caution icon appears next to the workpaper if the current workpaper has been modified after being signed off,"** but the help page describes no automatic reset. Clearing a sign-off "does not unreview the page's references" (same source). Caseware Cloud has the same blind spot under different labels. Its statuses run "Partially prepared" → "Prepared" → "Reviewed", plus a **"Modified since last review"** warning icon that shows the last reviewer's name and date. Nothing in the documentation says the sign-off is removed ([Caseware: signoff scheme](https://www.caseware.com/docs/en/cloud/global-reviewcomp/define-a-documents-signoff-scheme)). Caseware does show what changed, but only for checklists: its "Changes since last review" option "indicates responses that were changed after reviewer signoff" ([Caseware: review tools](https://www.caseware.com/docs/en/cloud/caseware-cloud/engagement-management/documentation-and-review/work-with-review-tools)). For other documents the reviewer sees only a warning, and in both products the stale sign-off is left in place.

Incumbents do get some things right. UltraTax CS updates its diagnostic messages "every time you add or change data", and "selecting a message will take you straight to the part of the return that needs your attention" ([UltraTax CS: Review diagnostic messages](https://www.thomsonreuters.com/en-us/help/ultratax-cs/errors/review-diagnostic-messages)). Blue chevrons mark fields that were filled last year but are blank this year, red chevrons mark overridden amounts, and a frozen "Watch" tab shows how chosen values have changed ([UltraTax CS: Review tools](https://www.thomsonreuters.com/en-us/help/ultratax-cs/miscellaneous/review-tools-and-features.html)). Overridden amounts are also listed on an "Input Screen Overrules" tab, which the research notes sourced from a search summary of [a separate settings page](https://cs.thomsonreuters.com/ua/ut/cs_us_en/utwapp/sysconfig/enable_notif_overruled_data.htm). CCH Axcess separates Preparer Notes, which carry forward year to year, from Reviewer Notes, which apply to the current year only. Each note records who raised it and who cleared it, and a Tax Return Dashboard lets the preparer self-check before hand-off ([Wolters Kluwer](https://www.wolterskluwer.com/ja-jp/expert-insights/onscreen-review-is-the-next-critical-stage-for-tax-workflow-improvement)). These features match what reviewers actually do. Reviewers are scarce because the role takes years of experience, and most of their queue time goes on **tie-out and completeness checks** ([EDUCBA](https://www.educba.com/tax-return-review/)). That source is weak, but the incumbents' own features point the same way: SPbinder's Review Tree exists to surface unreviewed fields, unreviewed stamps and uncleared notes ([SPbinder tour](https://www.thomsonreuters.com/en-us/help/sureprep/spbinder/get-started/a-brief-tour-getting-started)).

The hand-off itself looks immature. On **27 Jul 2026** SurePrep added **"Flagged for Review"**, which its release note calls "a new standardized status indicating the binder is ready for review and finalization" ([1040SCAN release notes](https://www.thomsonreuters.com/en-us/help/sureprep/release-notes/1040scan-release-notes/2026/2026-07-27-release--flag-a-binder--review-module-d)). My *inference* is that firms previously signalled hand-off with their own custom statuses. The note does not say that directly. In TaxDome, according to a search summary of its help page, sending work back is a pipeline move: stage automations must be reapplied when the job re-enters a stage, and the move is not tied to a review note ([TaxDome help](https://help.taxdome.com/article/920-tax-preparation-configure-processes-in-taxdome)). The reviewer's fetch of that page returned a 403, so this rests on the summary alone. Karbon's workflow help describes customizable statuses set from a drop-down, but says **nothing about send-back** ([Karbon help](https://help.karbonhq.com/en/articles/6085829-overview-of-workflow)), so how Karbon sends work back is undocumented. Users of Canopy, as reported by a competitor, complain that note tracking is limited and context is lost on complex jobs ([TaxDome blog](https://blog.taxdome.com/karbon-vs-canopy)). Users complain about how diagnostics are presented ("often poorly written and difficult to see", [Capterra: Taxprep](https://www.capterra.com/p/185193/Taxprep/reviews/?page=2)), and about software slowing down and glitching after mid-season updates ([G2: Lacerte](https://www.g2.com/products/lacerte/reviews)). The AI-native tax tools sell a source-linked "review-ready workpaper" with mismatch flags. Juno does this for more than 100 document types ([CPA Practice Advisor](https://www.cpapracticeadvisor.com/2026/07/15/firm360-introduces-autoprep/186752/)), and Instead gives reviewers findings "organized by severity" with citations ([Instead](https://instead.com/resources/blog/how-ai-tax-return-review-works-in-instead)). Their sign-off and send-back mechanics are not publicly documented, so no one can show that they close the gap. **Where the field fails, then, is in three places:** stale sign-offs that persist, send-back separated from the reason for it, and "what is left and what changed" spread across several tabs.

The client end of the review chain fails for its own reasons. Remote e-signature on Form 8879 requires knowledge-based authentication (KBA): multiple-choice questions about the client's past, such as a mortgage lender or a former address, repeated every year ([IRS FAQ](https://www.irs.gov/e-file-providers/frequently-asked-questions-for-irs-efile-signature-authorization)). Liscio's support site is reported to put KBA failure at **10–15%** of clients ([Liscio support: 8879 signature options](https://support.liscio.me/portal/en/kb/articles/8879-signatures-options-including-kba)). That is a vendor figure, and the page returned a 404 when I re-checked it, so treat the number as unconfirmed. The Mango Practice blog previously cited for it does not contain it. Three failed attempts force a wet signature ([Liscio](https://www.liscio.me/resources/form-8879-electronic-signature-guide-for-tax-preparers)). TaxDome sets the useful precedent of keeping client-facing statuses separate from internal ones and hiding internal comments from clients ([TaxDome](https://taxdome.com/en-au/client-portal)). I found no evidence that plain-language summaries or year-over-year comparisons make client approval easier. That idea is a hypothesis worth building, not a proven result.

## The selected item drives a right-hand evidence pane

Every best-in-class tool examined uses the same split. The left column holds navigation and history. The centre holds the thing being worked on. The right panel is a **dependent view of the current selection**: it is opened by the selection and can be dismissed. Claude moves "substantial, standalone content", typically more than 15 lines, into a separate side window, and keeps short content inline ([Claude Help](https://support.claude.com/en/articles/9487310-what-are-artifacts-and-how-do-i-use-them)). Linear opens an inbox notification as an editable issue beside the list ([Linear: Inbox](https://linear.app/docs/inbox)). A "Peek" preview toggled with Space appears only in a search snippet; its docs page returns 404, so it is **unverified** and is used here only as a design idea, not as cited practice. Figma keeps comments in the right sidebar ([Figma Help](https://help.figma.com/hc/en-us/articles/360041068574)). Hebbia's grid opens a cell to show its source passage and reasoning ([vantaige.io](https://vantaige.io/fr/ai-tool/hebbia), secondary source). Cursor shows the cost of getting this wrong. Users complain about a review panel that piles up edits and won't close, and about changes being auto-applied with no review UI ([Cursor forum](https://forum.cursor.com/t/review-panel-doesnt-dismiss-rendering-it-useless-reproduced-by-another-user-too/163722); [Cursor forum](https://forum.cursor.com/t/agent-mode-no-longer-shows-review-accept-interface-and-applies-file-changes-automatically-after-recent-update/152581)).

Click-to-source is where professional tools pull clearly ahead of consumer AI. DataSnipper's "Snips" extract a value from a source document and **automatically create a reference** to it, and its matching can require a field (left empty if not found, never guessed) and accept differences within a set tolerance ([DataSnipper](https://datasnipper.com/government-audit/grant-audit); [DataSnipper 3.0](https://www.datasnipper.com/resources/everything-you-need-to-know-about-datasnipper-3-0)). Harvey added "clickable references with highlights" ([Harvey 2Q 2024](https://help.harvey.ai/en/articles/9893976-harvey-update-2q-2024)), and its Review Tables can re-run columns **"without redoing verified work"** ([Harvey release notes](https://eu.help.harvey.ai/release-notes/page/4)). Consumer tools such as Perplexity stop at numbered footnotes. One finding matters for the design. Audit tools do show a "verified" state of sorts: Caseware has a "Reviewed" status and DataSnipper marks matches. But **none of the AI research tools examined (Claude, Hebbia, Harvey, Rogo, Perplexity) documents a confidence or verification state for each value in its UI.** A workpaper that shows, for each value, where it came from, how it was checked, and which checks it fails would join the audit tools' verification to the AI tools' source links. Neither group currently offers both. For a tax workpaper, the pattern is direct. Clicking a number, flag or citation chip in the centre loads the source document on the right, scrolled to a box around the exact field. Hovering or pressing Space previews it without moving focus (a design choice, not a cited convention). A number with no source is visibly different, because "unsourced" is a state in its own right.

The right panel must never be a modal. NN/g's case against modals is that they "block the content in the background", and that background can be the very information the user needs to decide ([NN/g](https://www.nngroup.com/articles/modal-nonmodal-dialog/)). A reviewer comparing a 1099 box with a return line needs to see both at once.

## GitHub's merge gates map onto tax sign-off

GitHub branch protection is the clearest model for a workpaper's review logic, because it treats approval as a condition that the system enforces. Approval is not a badge someone adds. **Stale approvals are dismissed** when new commits "affect the diff". Merging can require that **all conversations are resolved**, that required status checks are `successful`, `skipped` or `neutral`, and that **the most recent push is approved by someone other than its author** ([GitHub Docs](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches)). OpenSSF states the reasoning directly: any new change must be reviewed again ([OpenSSF](https://best.openssf.org/SCM-BestPractices/github/repository/dismisses_stale_reviews.html)). The edge cases teach as much as the rules. Users report that rebases which leave the code unchanged do not dismiss reviews, and others ask for approval to depend on whether the diff has actually changed, so that a squash that leaves the code the same keeps its approval ([GitHub community #12876](https://github.com/orgs/community/discussions/12876)). In a workpaper, the equivalent is to **invalidate a sign-off only when a value under it actually changes**, not on every save.

Translated, the mapping is direct. A stale approval becomes a sign-off scoped to the values it covers, which reverts to "needs re-review" and shows a one-line diff ("Box 1 changed from X to Y after review"). Required conversation resolution becomes **no partner sign-off and no release to the client while any review note is open**. Required checks become computed diagnostics (cross-foot checks, prior-year variance, source mismatch) that must pass or carry a written waiver; GitHub's "skipped" and "neutral" states are the waiver, recorded with a reason. The rule about the most recent push means that, **at reviewer level and above**, the person who last changed a value cannot sign it off. The preparer's L1 sign-off is a self-attestation in CPA practice ("I prepared this"), so the rule does not apply there. Applying it there would also break a demo where one person plays every role through the switcher. GitHub's admin bypass ([GitHub Docs](https://docs.github.com/de/enterprise-server@3.4/pull-requests/collaborating-with-pull-requests/reviewing-changes-in-pull-requests/about-pull-request-reviews)) becomes a partner override that is allowed but logged permanently. Sending work back should be one action that carries the open notes with it, which removes the split between notes and pipeline status seen in TaxDome.

Triage and history come from the same family of tools. Linear's inbox defaults to a **Priority** tab that "separates notifications that need your attention from other updates". It uses J/K to move, U to toggle read, H to snooze and Backspace to clear, and "Show unread first" as a display option ([Linear: Inbox](https://linear.app/docs/inbox)). Cursor's "jump to the next file with pending changes" ([Cursor docs](https://docs.cursor.com/agent/review)) becomes "next unseen change" for a reviewer coming back to a return. ChatGPT Canvas shows version arrows **only once a second version exists**, and "Show changes" marks removals in red and additions in green ([DataCamp](https://www.datacamp.com/blog/chatgpt-canvas)). That fits the packet's three computed return versions: compare two snapshots side by side, and hide the control when there is nothing to compare. Figma's complaint that version history is global and cannot show what changed in one frame ([Figma forum](https://forum.figma.com/t/version-history-allow-client-access-for-review-comments/61821)) argues for **history on each value**, not just on the whole file. Harvey makes History a top-level destination of its own ([Harvey Help](https://eu.help.harvey.ai/articles/getting-started-with-harvey)), which helps a reviewer who arrives cold.

## One layered screen serves both the new hire and the veteran

The research does not support separate "beginner" and "expert" modes. Nielsen's heuristic 7 asks for shortcuts for experienced users that are **"hidden from novices"**, layered over a default that is visible and recognisable ([NN/g heuristics](https://www.nngroup.com/articles/ten-usability-heuristics/)). Recognition beats recall because a list of options gives memory more cues than a blank prompt. NN/g draws the practical consequences: make functions visible, label icons, show recent items so users can resume, and prefer contextual tips to tutorials, because "tutorials have a lot of information, but they are not rehearsed much" ([NN/g](https://www.nngroup.com/articles/recognition-and-recall/)). Superhuman resolves the tension between these demands with its command palette. According to the research notes, its help centre said: "If you don't know a shortcut, just hit Cmd+K… You can see the shortcut for next time" ([Superhuman Help, as fetched for the notes](https://help.superhuman.com/article/441-splits)). That page now returns a 404 and its replacement ([Speed Up With Shortcuts](https://help.superhuman.com/hc/en-us/articles/45191759067411-Speed-Up-With-Shortcuts)) returned a 403 to me, so the wording cannot be reproduced, though the reviewer confirmed the idea on the newer page. The palette serves the new hire on day one, and over time it teaches them the shortcuts the veteran already uses. Linear's `?` shortcut sheet completes the pattern ([Linear](https://linear.app/enablement/guides/navigating-linear)).

Progressive disclosure has a hard limit: **"designs that go beyond 2 disclosure levels typically have low usability."** And because "the very fact that something appears on the initial display tells users that it's important" ([NN/g](https://www.nngroup.com/articles/progressive-disclosure/)), the first screen makes a claim about priority. For a workpaper, the first level is the value, its status and a one-line reason. The second level is the source, the checks and the history. There is no third. Job-centred design points the same way. The preparer's job is "find what's wrong before the reviewer does", and the reviewer's job is "confirm this return is right and defensible". Neither job is "browse 74 documents". The home screen should therefore be the open-issues queue beside the return summary, not a list of documents. Success is measured as task completion rate, recorded as labelled levels that are never averaged ([NN/g](https://www.nngroup.com/articles/success-rate-the-simplest-usability-metric/)).

Trust has its own rules, and the most counter-intuitive one is that admitting uncertainty builds reliance. Google PAIR says users should "calibrate their trust correctly". Saying that a result could be wrong lowers trust in that one result but builds reliance over the long term. Explanations should match the stakes ("Don't say 'what' without saying 'why' in a high stakes scenario"), and **"numeric confidence indicators are risky."** Categories need guidance on what to do at each level ([PAIR](https://pair.withgoogle.com/chapter/explainability-trust/)). A workpaper therefore shows "Needs review", "Matches source" or "Overridden", each with a next step, not "OCR 87%". Error handling follows Aza Raskin's rule, **"Never use a warning when you mean undo"**: people click through confirmation dialogs by reflex ([A List Apart](https://alistapart.com/article/neveruseawarning/)). Keep modal interruption for genuinely irreversible steps such as final sign-off or release to the client ([NN/g](https://www.nngroup.com/articles/modal-nonmodal-dialog/)). Hostile enterprise software, in the research's terms, has hidden state and leaks internal vocabulary. CPAs share tax vocabulary, so form-line names belong on screen. Packet internals (field keys, JSON paths, extraction IDs) belong only at the second level.

## WCAG 2.2 AA, semantic tokens and tabular figures set the floor for the build

WCAG 2.2, published as a W3C Recommendation on **5 Oct 2023** (the 12 Dec 2024 date on the TR page is a republication), is the conformance baseline ([W3C: New in 2.2](https://www.w3.org/WAI/standards-guidelines/wcag/new-in-22/)). Three of its nine new criteria, plus one carried over from WCAG 2.1, apply directly to a dense three-pane layout:

| Criterion | Requirement | Where it bites in the workpaper |
|---|---|---|
| 2.4.11 Focus Not Obscured | The focused element is never entirely hidden | Sticky headers and the right panel covering a focused row |
| 2.5.8 Target Size | At least 24×24 CSS px | Row action icons and source chips |
| 2.5.7 Dragging Movements | A single-pointer alternative to every drag | Resizable panes |
| 1.4.11 Non-text Contrast (from 2.1) | 3:1 for components and their states | Status pills and focus rings |

Text needs 4.5:1 contrast under 1.4.3 ([W3C TR](https://www.w3.org/TR/WCAG22/)). GitHub Primer shows how to keep colour honest: **semantic tokens tie each colour to a role** ("status, action, or emphasis"), and functional tokens make both colour modes follow automatically ([Primer](https://primer.style/foundations/color/overview)). Colour should carry meaning only through those status tokens, and each status also gets an icon or label so that colour is never the only cue. For number-heavy screens the conventions agree: **right-align numbers that are compared, using tabular lining figures**; left-align nominal numbers such as EINs and ZIP codes; align each header with its data ([Adobe Spectrum](https://spectrum.adobe.com/page/table); [Spiris](https://designsystem.spiris.se/development/documentation/docs/table/)); use thousands separators and a consistent number of decimals ([Alberta DS](https://design.alberta.ca/examples/display-numbers-in-a-table-so-they-can-be-scanned-easily)). Loading indicators follow wait time: nothing under 1 s, a skeleton or spinner from about 2 to 10 s, and a progress bar with an estimate above 10 s ([NN/g](https://www.nngroup.com/articles/skeleton-screens/)).

On the component stack, the shadcn/ui changelog shows components shipping for **Base UI, React Aria and Radix**, an entry titled **"Base UI as the Default" (Jul 2026)**, and new "Human in the Loop" and "Trace" components ([shadcn/ui changelog](https://ui.shadcn.com/docs/changelog)). Only the entry titles were read, not their full text. For a one-day build, shadcn/ui on Tailwind with its default primitive layer is the lowest-risk choice. The code lives in the repo and can be restyled, and the primitives handle focus, keyboard and ARIA. Optimistic saving with a visible "Saved · 12:04" indicator is recommended practice, but no primary source for it was fetched in this research.

## Conclusion

The tools examined suggest that trust in a workpaper does not come from how it looks. It comes from **guarantees the system enforces and the user can see**. A CPA trusts SPbinder's green tick only until the day it stays green on a figure that changed after sign-off. A sign-off that dismisses itself, a note that blocks release until it is resolved, and a number that cannot appear without a source chip are guarantees no warning icon can provide. They also lower the cost of review, which the evidence identifies as the bottleneck. The same structure that reassures the veteran teaches the new hire: a queue sorted by severity, plain-language reasons, and a source one click away explain the work better than any tour. The open risk is evidence, not design. Practitioner pain points rest on a handful of reviews and vendor blogs, and the AI-native competitors' review UX is undocumented in public. Testing with real users would be the next step before anything beyond this case study.

## Design rules for the mock-up and build

Each rule can be checked in the mock-up or covered by an automated test. The rules are in priority order for a one-day build. **Tier 1 is the demo core**: build it first, deploy it, then work down. "Brief" marks a rule that answers an explicit line in the brief (`docs/brief.txt`), so a later tier does not mean optional, only later.

### Tier 1: demo core (the ten rules to build first)

| # | Rule | Check |
|---|---|---|
| 1 · L1 | Three panes: left = "since you last looked" and history; centre = return or workpaper; right = evidence for the selection. Density tuned at **1440 px**, works at minimum 1280 px, right pane collapsible | Screenshots at 1440 and 1280 px show all three; collapse works |
| 2 · L2 | The right pane follows the selection, is non-modal, closes with Esc, and shows one item at a time | Click two values in turn; the pane shows only the second; Esc closes it; the centre value stays visible |
| 3 · P1 | Every computed or extracted number has a source chip; clicking it opens the simulated document with the field boxed | Test: every number on the return resolves to a document and field |
| 4 · P3 | A number with no source shows a distinct "Unsourced" state | Test: a fixture value without a source renders "Unsourced" |
| 5 · F1 | Every mistake in `docs/ground-truth/` appears as a flag with a plain-language reason and a link to the source *(brief)* | One test per ledger entry |
| 6 · F2 | Flags are sorted by severity; "Blocks filing" is a separate tab and the default | Default tab = blocking; order matches severity |
| 7 · F4 | The left sidebar opens on **"Since you last looked"** (changes and new flags since this role's last visit), then full history; "next unseen" and "mark all seen" actions *(brief)* | Change a value as role A; switching to role B shows it at the top of B's sidebar |
| 8 · G1+G2 | A sign-off covers named values and goes stale only when one of them actually changes. It then reverts to "Needs re-review" with a one-line diff; a re-save of the same value keeps it *(brief)* | Test: change a signed value → status flips and the diff is logged; re-save unchanged → sign-off holds |
| 9 · G3 | Partner sign-off and client release are disabled while any review note is open or any blocking check fails without a waiver; the button names what is blocking it *(brief)* | Test: open note → button disabled, label names the note |
| 10 · R1+L4 | The header always shows **role and identity, return version, stage and save state**. Switching role visibly changes the banner, the queue, the available actions and the vocabulary (per-role actions in R1 below); client view hides internal notes and statuses *(brief)* | Switch through every role; each shows its banner, its queue and only its actions; client view contains no internal text |

**R1, the actions for each role** (what the switcher must visibly change):

| Role | Can | Cannot see or do |
|---|---|---|
| Preparer | Edit values with a reason, answer notes, L1 sign-off, flag for review | Partner sign-off, release |
| Reviewer | Raise and clear notes, L2 sign-off, send back | Edit values without a logged reason |
| Partner | Final sign-off, logged override with a reason, release to client | — |
| Client | Read the plain summary, answer questions, approve and sign | Internal notes, internal statuses, flags |
| Administrator | Assign work, set deadlines, read view logs | Sign-off |
| Next year's preparer | Read prior-year record, carry items forward | Edit the filed year |
| IRS examiner | Read the frozen filed record (X1) | Any edit; any internal draft state after filing |

### Tier 2: the rest of the brief, after the core is live

| # | Rule | Check |
|---|---|---|
| C1 | **Several people at once** *(brief)*: show who else is viewing the return; another person's change appears live and joins "since you last looked"; an edit to a value someone changed after you loaded it shows a conflict notice, never a silent overwrite | Two browser tabs as two roles: an edit in one appears in the other within 5 s; a conflicting edit shows the notice |
| X1 | **Examiner's frozen record** *(brief)*: filing freezes a read-only snapshot with a timestamp; the examiner role sees only that snapshot, with sources, notes, sign-offs and history intact; amendments sit on top as a new version | As examiner, every edit control is absent; post-filing edits do not appear in the snapshot |
| R2 | **Client approval and KBA** *(brief)*: one screen with refund or amount due and the main changes from last year, then a sign step that states identity verification (KBA) is required every year, shows the KBA step (simulated), and shows a visible wet-signature fallback after three failed attempts | The client flow shows the summary, the KBA step, and the fallback after three simulated failures |
| G4 | **At reviewer level and above**, the person who last changed a value cannot sign it off. The L1 preparer sign-off is exempt (self-attestation) | Test: as reviewer, edit then sign → blocked; as preparer, edit then L1-sign → allowed |
| G5 | A partner override is allowed but logged permanently with a reason | The override appears in history |
| G6 | Send-back is one action that carries the open notes into the preparer's queue | Test: send back → the notes appear for the preparer |
| P4 | Confidence is shown as categories that tell the user what to do ("Matches source", "Needs review", "Overridden", "Conflicts"), never as a percentage at level 1. A single mapping function turns the packet's numeric confidence into a category, with thresholds in one config set from the packet README. The raw number appears only at level 2 | Unit test on the mapping function; no "%" beside a level-1 confidence label |
| P5 | A required field that is missing is shown empty and flagged, never guessed | Test: the missing-field fixture renders blank with a flag |
| H1 | Each value has its own history (who, when, old → new, why, tax effect) *(brief)* | Open history on any value |
| H3 | Edits are undone, not confirmed: every edit or bulk action shows an undo toast; a modal appears only for final sign-off, release and filing *(brief: "act on many items at once, with undo")* | Bulk-resolve 5 flags, undo restores all 5; only those three confirm dialogs exist |
| H2 | Compare any two of the packet's three return versions, with changes marked by more than colour alone *(brief)* | Diff two computed versions; changed lines carry a +/− marker |
| F3 | Triage keys: J/K move, Enter opens, R resolves, W waives (asks for a reason), S snoozes, U toggles unread, `?` opens the shortcut sheet | Playwright keyboard-only run triages three flags |
