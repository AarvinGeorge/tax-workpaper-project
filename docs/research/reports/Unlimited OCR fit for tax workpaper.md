# Skip Unlimited-OCR; design the anchor instead

**Do not use baidu/Unlimited-OCR in the one-day build.** It is a real, capable, MIT-licensed document-OCR model from Baidu, but it has nothing to read here, and it would cost hours we do not have. The packet has no page images, only extracted values with 0–1 page boxes. The brief tells us to "start where our extraction stops" and to build simulated documents that real ones "could replace seamlessly". Running OCR over pages the app renders from the packet's own text is circular: it would "verify" text we typed ourselves. None of the 27 logged mistakes is a reading error a better OCR would catch. They are wrong inputs, missed documents and rules applied too simply. The model needs an NVIDIA GPU, 6.7 GB of weights and `trust_remote_code`, so it cannot run on Vercel Functions. A separate GPU host would take about 2–4 hours to stand up. The useful takeaway is the pattern the tax industry already uses: OCR is one swappable part, and the product is the anchor, confidence and verification layer around it. So: build that layer now with zero OCR, prove "seamless replacement" with one fixture-based contract test, and give Unlimited-OCR one paragraph in the write-up. It is the right self-hosted reader for long brokerage PDFs in a real product.

## A 3.3B-parameter page reader, popular but thinly maintained

Unlimited-OCR is a continued-training derivative of DeepSeek-OCR, released on **22 Jun 2026** with the paper arXiv 2606.23050 ([README](https://github.com/baidu/Unlimited-OCR); [arXiv](https://arxiv.org/abs/2606.23050)). Its one new idea is "Reference Sliding Window Attention". Each output token attends to all the page's visual tokens but only the previous 128 output tokens. That keeps memory flat, so it can transcribe **dozens of pages in one pass** within a 32K context. "Unlimited" means long documents, not an unlimited service. The model is a Mixture-of-Experts with **3,336,106,240 parameters, about 0.5B active per token**, stored as a 6.67 GB BF16 safetensors file ([HF API](https://huggingface.co/api/models/baidu/Unlimited-OCR); [config.json](https://huggingface.co/baidu/Unlimited-OCR/blob/main/config.json)). It parses pages into Markdown-like text, with tables as HTML. Each layout block is tagged `<|det|>label [x1,y1,x2,y2]<|/det|>`, using labels such as text, title, table, header and page_number ([issue #51](https://github.com/baidu/Unlimited-OCR/issues/51); [issue #16](https://github.com/baidu/Unlimited-OCR/issues/16)). The maintainer says it "mainly support[s] Chinese and English" ([issue #25](https://github.com/baidu/Unlimited-OCR/issues/25)).

It does **not** extract semantic fields. It will transcribe a W-2, but it will not tell you "Box 1 = 85,000". It also gives no confidence score per field or per character. Its boxes are **block-level only** (a paragraph or a table cell region, not a word or a number). They are normalised to a 0–999 grid: the model code scales them with `x1 / 999 * image_width` ([modeling_unlimitedocr.py](https://huggingface.co/baidu/Unlimited-OCR/blob/main/modeling_unlimitedocr.py)). The README does not document this, which is why one research note calls the format undocumented. The code settles it. In multi-page mode the output does not mark page boundaries, so mapping a box back to its page takes extra work ([AIreiter](https://aireiter.com/blog/unlimited-ocr-baidu-api-review)).

**The licence is clean: MIT for code and weights** ([LICENSE](https://github.com/baidu/Unlimited-OCR/blob/main/LICENSE); [HF card](https://huggingface.co/baidu/Unlimited-OCR)). One inherited file carries an Apache-2.0 header ([modeling_deepseekv2.py](https://huggingface.co/baidu/Unlimited-OCR/blob/main/modeling_deepseekv2.py)). Uptake is strong but maintenance is not. As of 16 Oct 2026 the repo has **27,512 stars and 1.16M Hugging Face downloads**, but also **2 contributors, 14 commits (13 of them README edits), no releases or tags**, and 57 open issues against 10 closed ([GitHub API](https://api.github.com/repos/baidu/Unlimited-OCR/contributors); [commits](https://github.com/baidu/Unlimited-OCR/commits/main); [HF API](https://huggingface.co/api/models/baidu/Unlimited-OCR)). The GitHub repo is a thin wrapper: a README, one batch script and a bundled custom SGLang wheel. The model code lives on Hugging Face. An official Docker image was promised in June and has not shipped ([issue #27](https://github.com/baidu/Unlimited-OCR/issues/27)). Treat it as a strong research release, not a maintained product. Anyone who adopts it should expect to own the fixes.

## Accuracy is near the top, but its weak spots are the dangerous ones for tax

Baidu reports **93.23 on OmniDocBench v1.5 and 93.92 on v1.6**, against DeepSeek-OCR's 87.01 ([paper, Table 1](https://arxiv.org/abs/2606.23050)). The benchmark's own maintainers listed it on 11 Sep 2026 at **94.00 on v1.6_full**. That places it **sixth**, behind PaddleOCR-VL-1.6 (96.34), MinerU2.5-Pro (95.75), GLM-OCR (95.22) and two other PaddleOCR-VL versions ([OmniDocBench](https://github.com/opendatalab/OmniDocBench)). It is strong, but not the leader, and several of the models ahead of it are smaller. One independent evaluator used the official scorer and got **92.45 overall, with text edit distance 0.087 against Baidu's implied 0.042**. Re-scoring Baidu's own shared predictions gave 0.085. The thread was still unresolved on 1 Aug ([issue #66](https://github.com/baidu/Unlimited-OCR/issues/66)). Its accuracy on long documents also drops with length: edit distance goes from **0.036 at 2 pages to 0.107 at 40+ pages**, which Baidu puts down to small text at the 1024×1024 multi-page resolution ([paper, Table 3](https://arxiv.org/abs/2606.23050)). No benchmark covers US tax forms.

The known failures matter more than the headline score. On **0.2–1.2% of pages the output repeats until it hits the length limit**. The built-in repetition guard misses short repeats, and tightening it globally dropped one evaluator's score from 91.97 to 64.56 ([issue #55](https://github.com/baidu/Unlimited-OCR/issues/55)). Other reports describe complex scanned tables degrading in multi-page mode ([#16](https://github.com/baidu/Unlimited-OCR/issues/16)), rotated text dropping lines and inventing a new one ([#79](https://github.com/baidu/Unlimited-OCR/issues/79)), and boxes missing or overflowing ([#33](https://github.com/baidu/Unlimited-OCR/issues/33)). This is the generative-OCR failure mode. A vision-language model "can invent text that was never on the page", fills unclear digits with what seems to fit, and offers "no per-character score to threshold on" ([Towards AI](https://pub.towardsai.net/vlm-validation-and-document-intelligence-ed609460e8d4)). A financial OCR benchmark shows the result: "21,829,000" read where the source says "21,429,000" ([FinCriticalED, arXiv 2511.14998](https://arxiv.org/pdf/2511.14998)). A confidently wrong digit is exactly what this case study is about. Any number such a model produces would need an independent cross-check before a preparer could trust it.

## The tax industry treats OCR as a part and competes on verification

Every incumbent follows the same pipeline: classify and bookmark documents, extract fields into fixed form templates, verify, send exceptions to a human, then export. **SurePrep (Thomson Reuters)** checks native PDFs against their own text layer and highlights the auto-verified fields in pink. It sends a page to human verification when an identifier does not match the client's prior-year proforma, a required field such as SSN is missing, or the page was not fully auto-verified ([TR help: auto verification](https://www.thomsonreuters.com/en-us/help/sureprep/1040scan/auto-verification)). **Intuit's Lacerte Tax Import** uses "dual optical character readers" and returns **bookmarked, highlighted PDFs showing where each value came from** ([Intuit](https://accountants.intuit.com/lacerte/integrations/tax-import/)). **GruntWorx** turns consolidated 1099-Bs into one spreadsheet row per lot and reviews the category totals ([Drake KB](https://kb.drakesoftware.com/kb/GruntWorx/11043.htm)). Newer entrants sell the same idea. Black Ore's Tax Autopilot, broadly available since 29 Apr 2026, "links each data point back to source documents, and flags items requiring attention" ([CPA Practice Advisor](https://www.cpapracticeadvisor.com/2026/04/29/black-ore-launches-tax-autopilot-for-broad-availability/)). In audit, DataSnipper's "Snips" tie an Excel cell to a region of a source document ([DataSnipper](https://datasnipper.com/features/match)). None of them publishes its anchor format. "Highlighted where each value came from" still implies the same thing every time: a page plus a region.

Here is how the main engines compare for a tax workpaper:

| Option | Tax field schema | Per-field confidence | Boxes | Runs where | Fit |
|---|---|---|---|---|---|
| **Azure Document Intelligence v4** | Yes: W-2, 1098 family, about 20 1099 types incl. 1099-B and Combo, 1040 and schedules | Yes | Yes | Microsoft cloud | Broadest tax coverage off the shelf ([Microsoft Learn](https://learn.microsoft.com/en-us/azure/ai-services/document-intelligence/prebuilt/tax-document)) |

| **Google Document AI** | W-2 parser at $0.30/document ([pricing](https://cloud.google.com/document-ai/pricing)) | Yes | Yes | Google cloud | Narrower tax set |

| **Unlimited-OCR** | No | No | Blocks, 0–999 grid | Self-hosted NVIDIA GPU, or Baidu Cloud | Best idea for 40+ page broker PDFs in one pass |

So the open-source models, Unlimited-OCR included, compete on transcribing layout. The cloud APIs compete on tax-field schemas with confidence. Either way, the tax products differ mainly in their verification layer. That is the layer the case study asks us to design.

## Nothing to read, no GPU to run on, and real data protection costs

**The circularity problem decides it.** The packet holds **74 documents, 199 pages and 3,012 extracted values, every one with a 0–1 page box, and no page images** ([evidence notes](../../discovery/01-evidence.md)). Our simulated pages would be rendered from the packet's printed content. OCR would read that text back with some noise, so any disagreement would be an OCR error or a rendering bug, never a packet mistake. It would show a green "verified" result that tested nothing. The mistake ledger makes the same point from the other side. All 27 findings are "a wrong input, a missed document, or a rule applied too simply". The engine's arithmetic is sound (148 of 221 formula lines recomputed, 0 mismatches) ([ground-truth ledger](../../ground-truth/README.md)). Only a handful are reading errors at all. GT-A05 is Theo's SSN transposed (…3309 against …3390 on the card), which caused the July e-file rejection. GT-A07 is a tax ID misread at 0.97 confidence. GT-A01 and GT-B03 are blanks read as 0. A second reader would catch these only on real images: the SSN card D71 is a photo the packet does not include. The other patterns are cross-document, prior-year and client-answer conflicts, and a better reader would reproduce every one of them.

**Deployment closes the door.** Vercel Functions have no GPU, at most 4 GB of memory and a 4.5 MB request body limit ([Vercel limits](https://vercel.com/docs/functions/limitations)). Unlimited-OCR's supported paths all need CUDA. The vLLM recipe says ≥8 GB VRAM ([vLLM recipe](https://recipes.vllm.ai/baidu/Unlimited-OCR)), and one practitioner saw about 12 GB in use ([AIreiter](https://aireiter.com/blog/unlimited-ocr-baidu-api-review)). On CPU it needs a patch to remove about 17 hardcoded `.cuda()` calls, and it then takes **~550 s for one dense page** ([issue #81](https://github.com/baidu/Unlimited-OCR/issues/81)). Even on a T4 GPU it ran **14.6–30.9 s per page, 8–19× slower than Tesseract** ([issue #100](https://github.com/baidu/Unlimited-OCR/issues/100)). No Hugging Face inference provider serves it. Running it would mean a Modal or HF Endpoints GPU at about $0.60–0.80/h ([Modal pricing](https://modal.com/pricing); [HF Endpoints pricing](https://huggingface.co/docs/inference-endpoints/pricing)). The money is trivial; the time is not. Wrapping, uploading, parsing the `<|det|>` output, normalising boxes, handling failures and coping with a ~6.7 GB cold start comes to an estimated **2–4 hours**, against a **21:00 EDT Friday deadline** ([project CLAUDE.md](../../../CLAUDE.md)). Self-hosting also runs downloaded Python via `trust_remote_code`, and that code calls `eval()` on a string the model generated ([modeling_unlimitedocr.py](https://huggingface.co/baidu/Unlimited-OCR/blob/main/modeling_unlimitedocr.py)). That is acceptable with a pinned, reviewed revision, but it is not something to take on in a rush.

**For real client data, where the reader runs is a legal question.** Sending return information to an OCR service is a disclosure under 26 CFR 301.7216. If the recipient is outside the U.S., "the taxpayer's consent … prior to any disclosure is required" ([26 CFR 301.7216-2](https://www.law.cornell.edu/cfr/text/26/301.7216-2)). The FTC Safeguards Rule also requires service providers to be bound by contract, assessed periodically, and to encrypt the data ([16 CFR 314.4](https://www.law.cornell.edu/cfr/text/16/314.4)). Baidu's hosted API states no data region or retention policy, and its result links stay live for 30 days ([Baidu Cloud doc](https://cloud.baidu.com/doc/OCR/s/fmr1p39gb)). That rules it out for SSNs. Ranked from cleanest to worst: browser-side OCR (the image never leaves the machine), MIT weights self-hosted in a U.S. region, a U.S. cloud API under contract, then public demo Spaces or Baidu Cloud. The packet's household is invented, so this belongs in the write-up, not the build. It is one more point where the MIT licence is Unlimited-OCR's real advantage in a production version: the firm can host it itself.

### What to do, by priority

| Action | When | Why |
|---|---|---|
| Store each value's anchor as **document, version/hash, page, field id, 0–1 box, plus the quoted text with context** | Now, in the data model | Works with any reader. Textract's boxes drop straight in; Unlimited-OCR's need a ÷999 scale. The quoted text lets a link re-find its value when a corrected document shifts the layout, following Hypothesis-style fuzzy re-anchoring ([Hypothesis](https://web.hypothes.is/blog/fuzzy-anchoring/)). If the value itself changed, flag "source changed" rather than re-anchoring silently. |
| Carry a **read state** (read / nothing printed / unreadable) and a **reader** (pipeline / second reader / human) on each value | Now | Makes the blank-read-as-0 mistakes (GT-A01, GT-B03) visible as data. OCR becomes one producer of that state. |
| One **contract test**: a hand-made, OCR-shaped box list for one simulated page must resolve to the same links | Now, about 30 min | Proves "real PDFs replace simulated ones seamlessly" without any model. |
| One write-up paragraph: a real-PDF adapter that joins any OCR's page boxes to field ids by text match plus overlap; a second read reserved for identifiers; Unlimited-OCR self-hosted in a U.S. region for long broker statements | Write-up | Answers the brief's replacement question and shows we know the field. |
| tesseract.js on attached evidence images, so a user can search the text and drag a box to link it to a line | Only after the deployed core surfaces all 27 mistakes; about 1 h | Fits Vercel, sends nothing anywhere. The brief only asks that files can be *attached*. |
| Unlimited-OCR on a GPU host; OCR over simulated pages; any public OCR endpoint | Skip | Hours of risk, nothing real to read, and a result that verifies nothing. |

## Conclusion

The question "should we use this OCR?" turns out to be the wrong one for this brief. The brief pays for the layer that every serious tax product competes on: provenance, confidence and the checks a value fails. The OCR engine is a replaceable input to that layer. Unlimited-OCR still sharpens the design. Its 0–999 block boxes, missing per-field confidence and occasional invented text are exactly what the data model must absorb from any future reader. If the model handles Textract's 0–1 word boxes, Unlimited-OCR's blocks and a human's drag-box equally well, the "seamless replacement" requirement is met by design rather than by demo.

Two things remain unknown and are worth saying plainly in the hand-in. First, Unlimited-OCR's accuracy on US tax forms has never been measured, and its headline text score has not been independently reproduced. Second, whether the founder would value a visible "AI reads documents" moment in the video over a complete core is Aarvin's call, not something research can settle. The evidence favours the core.
