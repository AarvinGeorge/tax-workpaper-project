# Two clocks, one cursor, no rewrites

No off-the-shelf product should be adopted for the workpaper's story clock: the app already has the shape that the mature temporal systems converge on, and the useful work is borrowing their semantics rather than their code. Every system surveyed, from XTDB and Datomic to SQL:2011 system-versioned tables, Marten and accounting ERPs, treats a past view as an immutable read, applies a correction as a new linked record, and gates any rewrite of history behind a privileged, explicitly destructive step. The workpaper's design (append-only event log, read-only packet, past view-only, no branches, filed return locked with amendments on top) maps cleanly onto the two classic time axes: the packet's `computed_at` is valid time, the app's event log is record time, and the story clock is a single cursor that cuts both. The strongest domain precedents come from tax and audit themselves: Form 1040-X is literally "original plus net change equals corrected, with a reason," IRS transcripts already separate a frozen as-filed record from a current account view, and US audit standards fix a completion date after which additions must name who, when and why. The main open risk is not technical but human: Fowler names educating users on two time axes as the hardest part of bitemporal systems, and no surveyed product moves one shared clock for every user at once, so the banner, labels and single exit back to "latest" carry more weight than any storage choice.

## Free temporal engines agree on immutable pasts and appended corrections

The surveyed systems fall into three families. **Bitemporal engines** keep two separate axes; XTDB (MPL-2.0) "implements the bitemporal functionality as specified in the SQL:2011 standard" and lets you record "when that data is, was, or will become valid in your business domain" ([xtdb GitHub](https://github.com/xtdb/xtdb)). Its docs state flatly that "users (rightly) have no control over system-time," and that `FOR VALID_TIME AS OF` yields the curated view with corrections while `FOR SYSTEM_TIME AS OF` yields what was known then, without them ([XTDB: Time in XTDB](https://docs.xtdb.com/about/time-in-xtdb.html)). **Transaction-time-only stores** such as Datomic model each fact as an immutable datom, and "a db is a point-in-time, immutable value and will never change" ([Datomic data model](https://docs.datomic.com/whatis/data-model.html)). Datomic has been free since April 2023 under Apache-2.0 binaries but is not open source ([Datomic blog](https://blog.datomic.com/2023/04/datomic-is-free.html); [Datomic Cloud FAQ](https://www.datomic.com/cloud-faq.html)). **Event stores** rebuild state by replay: Marten (MIT, on PostgreSQL) aggregates a stream up to a version or a timestamp and offers inline, async and live projection lifecycles ([Marten: Projections](https://martendb.io/events/projections/)).

| System | Licence | Time axes | Past rewritable? | Lesson for the workpaper |
|---|---|---|---|---|
| XTDB | MPL-2.0 (OSS) | Valid + system | System time never | `computed_at` is valid time; the log is system time |
| Datomic | Free Apache-2.0 binaries, closed source | Transaction only | No; retraction is a new datom | `as-of` is a read-only filter; corrections carry `:correction/for` |
| MariaDB system versioning | GPLv2 (not re-verified) | System (+ app time) | Only via privileged `DELETE HISTORY` | Enforce append-only at the database |
| SQL Server temporal | Proprietary, free docs | System only | No | Half-open `ValidFrom <= t AND ValidTo > t` lookup |
| PostgreSQL 18 | PostgreSQL License | Application-time constraints | n/a | `WITHOUT OVERLAPS` keys exist natively now |
| Marten | MIT | Event stream | No | Live replay is fine for small logs; inline cache if needed |
| Dolt / TerminusDB | Apache-2.0 (Dolt not re-verified) | Commit graph | Branch-first | Counter-model; do not copy branching |
| KurrentDB | KLv1, source-available, not OSI | Event stream | No | Free to use, licence shifting toward enterprise |

The table's last column is the point. On correction, the systems are unanimous: Datomic records a retraction as a new datom and lets a transaction entity carry an attribute like `:correction/for` naming the transaction it corrects ([Datomic data model](https://docs.datomic.com/whatis/data-model.html)); XTDB closes the old row's valid range and adds a new row, both system-stamped, so the earlier belief stays queryable ([XTDB](https://docs.xtdb.com/about/time-in-xtdb.html)); MariaDB requires a special privilege for `DELETE HISTORY` "to protect the integrity of the history" ([MariaDB](https://mariadb.com/docs/server/reference/sql-structure/temporal-tables/system-versioned-tables)). On branching, Datomic deliberately combines `with` and `as-of` so that it "does not let you branch the past" ([Datomic filters](https://docs.datomic.com/reference/filters.html)), which is exactly the workpaper's rule, while Dolt and TerminusDB are built around branches and commits ([Dolt docs](https://docs.dolthub.com/sql-reference/version-control/querying-history); [TerminusDB docs](https://terminusdb.com/docs/time-travel-to-previous-commits)) and are the wrong model.

Licensing matters if anything is embedded. XTDB, Marten, TerminusDB and the `periods` Postgres extension are OSI open source; Datomic and KurrentDB are free but not open source, and KurrentDB's planned 26.2 moves clustering, replicas and archiving behind an enterprise licence ([Kurrent blog](https://kurrentdb.kurrent.io/blog/licensing-in-kurrentdb-v26-2-and-beyond-what-s-free-and-what-s-licensed)). PostgreSQL 18 now ships application-time `WITHOUT OVERLAPS` keys and temporal foreign keys ([PostgreSQL 18 release notes](https://www.postgresql.org/docs/release/18/)), but core Postgres still lacks `FOR SYSTEM_TIME`; the `periods` extension fills that gap only through functions and is tagged proof-of-concept for PG 9.5 to 15 ([xocolatl/periods](https://github.com/xocolatl/periods)). None of this is worth adding to a single-household app whose log holds tens to hundreds of events.

## The story clock is a record-time cursor that also picks a valid-time version

The cleanest data model treats the two clocks as Fowler's two axes: actual time is "when something was true," record time is "when we learned it," and record history is append-only ([Fowler: Bitemporal History](https://martinfowler.com/articles/bitemporal-history.html)). The packet's three return versions, each stamped `computed_at`, are valid-time facts supplied by the data, which XTDB's guidance places on the valid axis because "as of" and "with effect from" phrasing signals valid time ([XTDB](https://docs.xtdb.com/about/time-in-xtdb.html)). The app's own events are record-time facts. The story clock therefore resolves to one function: the return version is the latest one whose `computed_at` falls at or before story time, using SQL Server's half-open `ValidFrom <= t AND ValidTo > t` convention so that a boundary instant never matches two versions ([Microsoft Learn: Temporal tables](https://learn.microsoft.com/en-us/sql/relational-databases/tables/temporal-tables)), and the work done is every event at or before the cursor.

Three implementation details follow from documented pitfalls. First, **key "latest point reached" on a monotonic sequence, not wall-clock time.** Datomic warns that an instant "is not as precise as Datomic's t or tx values" ([Datomic filters](https://docs.datomic.com/reference/filters.html)), SQL Server gives every row in a transaction the same begin time ([Microsoft Learn](https://learn.microsoft.com/en-us/sql/relational-databases/tables/temporal-tables)), and MariaDB's `AS OF TRANSACTION` excludes rows inserted before a point but committed after it ([MariaDB](https://mariadb.com/docs/server/reference/sql-structure/temporal-tables/system-versioned-tables)). A sequence makes "may act only at the head" an exact equality test, `cursor == head_seq`. Second, **never apply current derived logic to past data.** Dolt's `AS OF` on a view uses the view's current definition over historical rows ([Dolt docs](https://docs.dolthub.com/sql-reference/version-control/querying-history)), and Marten projections must be rebuilt when their code changes ([Marten](https://martendb.io/events/projections/)); the workpaper equivalent is rendering a past moment with the latest return version instead of the version current at that moment, and it deserves a test. Third, **replay is cheap at this scale.** Marten's live lifecycle recalculates aggregates on each request ([Marten](https://martendb.io/events/projections/)), and Fowler notes state "is purely derivable from the event log" so caching is optional ([Fowler: Event Sourcing](https://martinfowler.com/eaaDev/EventSourcing.html)); if a head cache is ever added, Marten's inline lifecycle, updated in the same unit of work as the append, keeps the head from going stale.

Amendments and corrections should be appended events that reference what they correct, following Datomic's `:correction/for` pattern, never an update of an old row. Append-only should be enforced in Postgres itself, by revoking UPDATE and DELETE on the events table or raising from a trigger, so that the view-only past is a database guarantee, mirroring MariaDB's privileged-only history deletion. Fowler adds a caution that matters for a tax tool: correcting the record does not undo effects already acted on, such as a payment already made, which need compensating actions ([Fowler: Bitemporal History](https://martinfowler.com/articles/bitemporal-history.html)). Replay also must not re-fire side effects; Fowler recommends gateways that are disabled during replay ([Fowler: Event Sourcing](https://martinfowler.com/eaaDev/EventSourcing.html)). One honest gap: no source models a user-advanced clock separate from both wall time and data time, so the story clock itself is app-specific, though hledger's `--today=DATE` override is a precedent for an explicit, user-set reporting "today" ([hledger manual](https://hledger.org/hledger.html)).

## Tax and audit practice already define the lock-then-amend grammar

Accounting systems share one lifecycle: draft, then submitted and locked, then corrected by a new linked record. Frappe's `docstatus` runs Draft, Submitted, Cancelled, and submitted documents cannot be edited except for explicitly allowed fields ([Frappe docs](https://docs.frappe.io/framework/doctypes/docstatus)); a correction is a cancel-then-amend that creates a new draft linked by `amended_from`, though the suffix naming detail rests on third-party sources ([frappe-mcp-server](https://glama.ai/mcp/servers/@appliedrelevance/frappe-mcp-server/tools/amend_document)). Odoo's lock date "prevents modifications to any posted journal entries," pushes a would-be backdated entry to the day after the lock date, logs administrator exceptions in the company chatter, and offers a hard lock that "cannot be changed or overridden, regardless of access rights" ([Odoo 18 docs](https://www.odoo.com/documentation/18.0/applications/finance/accounting/reporting/year_end.html)). ERPNext separates closing from locking: its Period Closing Voucher "does not erase history or stop backdated entries," and it "does not silently rewrite the submitted voucher" ([ERPNext docs](https://docs.frappe.io/erpnext/user/manual/en/period-closing-voucher)). Acceptance of the filed return maps onto Frappe's Submitted state and Odoo's hard lock; an amendment maps onto an `amended_from` child.

Form 1040-X is the same structure in IRS form. Column A reflects "the amount to which your originally filed return was adjusted," column B is "the net increase or decrease for each line that you are changing," column C carries unchanged lines from A, and Part II exists because "the IRS needs to know why you are filing" ([IRS Instructions for Form 1040-X](https://www.irs.gov/instructions/i1040x)). Amendments stack, "more than once, as long as each Form 1040-X is filed timely," and up to three can be e-filed per year ([IRS i1040x](https://www.irs.gov/instructions/i1040x); [IRS: File an amended return](https://www.irs.gov/filing/file-an-amended-return)). The data model that falls out is an immutable original snapshot plus an ordered list of deltas, each with a reason, where column A of amendment n equals column C of amendment n-1, which is a strictly linear history with no branches. California follows suit with an amended Form 540 plus Schedule X explaining the reasons ([FTB Schedule X instructions](https://www.ftb.ca.gov/forms/2020/2020-540-x-instructions.html)); calling it "540X" for tax year 2025 would be a domain error, since that form name dates from the pre-2016 era ([FTB 2015 540X](https://www.ftb.ca.gov/forms/2015/15_540X.pdf)). IRS transcripts supply the labelling: the return transcript "doesn't show any changes made after the original return was filed," while the account transcript "will show changes made after the original return was filed" ([IRS Tax Tip 2026-65](https://www.irs.gov/newsroom/tax-transcripts-know-the-different-types-and-how-to-get-them)). The workpaper should present "as filed" and "as now known" with exactly that split.

Audit standards supply the rule for who, when and why. AICPA AU-C 230 requires assembly within 60 days of the report release date, forbids deleting documentation before the retention period ends, and requires any later modification to record "the specific reasons" and "when and by whom they were made and reviewed" ([open-exam-prep AU-C 230 guide](https://open-exam-prep.com/study-guides/cpa-aud/final-evaluation-documentation/audit-documentation-retention)). PCAOB AS 1215 sets a 14-day documentation completion date for public-company audits ([legalclarity.org](https://legalclarity.org/audit-documentation-standards-requirements-and-penalties/)), and the PCAOB has disciplined a partner over undocumented post-completion workpaper changes ([Accounting Today](https://www.accountingtoday.com/news/pcaob-censures-bars-partner-for-failing-to-cooperate-with-inspection)). Both rest on secondary sources here because the primary texts were paywalled or blocked, so wording should be checked before quoting them in the hand-in. CaseWare Working Papers, the commercial reference, treats sign-off as a role-based per-document event with a "Reverse a Sign Off" action and a "History and Milestones" log ([CaseWare 2016 help](https://documentation.caseware.com/2016/WorkingPapers/en/Content/Engagement_Management/Electronic_Review_and_Signoff/c_ElectronicReview_and_SignOff_About.htm)), which argues for modelling sign-offs and their reversals as events in the log, not as mutable flags. One gap remains: no IRS primary text was found stating outright that an accepted e-filed return cannot be changed and must be amended, though the 1040-X instructions imply it.

## Interfaces signal the past weakly, so the workpaper must signal it loudly

Document-history products share one shape: a panel of discrete, labelled stops, a way back to current, and restore as a separate deliberate action. Google Docs opens history in a right panel, filters to "Only show named versions," and exits with a Back button that "returns you to the current version" ([Google Docs Help](https://support.google.com/docs/answer/190843)). Figma's past versions are effectively view-only, exit through "Edit current version," and describe no banner ([Figma Help](https://help.figma.com/hc/en-us/articles/360038006754)); Figma's forum shows the cost, with users reporting "can't edit restored version from history, view only" and restores that revert on Done ([Figma forum](https://forum.figma.com/archive-21/can-t-edit-restored-version-from-history-view-only-791)). The clearest past signal comes from MediaWiki: "This is an old revision of this page, as edited by [who] at [when]," with a note that the URL is a permanent link ([MediaWiki:Revision-info](https://en.wikipedia.org/wiki/MediaWiki:Revision-info)), and Wikimedia deliberately hides the "Last edited … ago" footer on old revisions so no "now" cue leaks into the past ([Phabricator T153125](https://phabricator.wikimedia.org/T153125)). Accounting tools add a visible boundary, GnuCash's red line at its read-only threshold ([GnuCash manual](https://lists.gnucash.org/docs/C/gnucash-manual/book-options.html)), and a strict cut: Fava's time filter removes "all the entries after the end date" and rolls earlier ones into opening balances ([Fava help](https://github.com/beancount/fava/blob/main/src/fava/help/filters.md)).

The closest analogues to a whole-workspace story clock are time-travel debuggers and imagery timelines, where the entire view re-renders at a discrete point. Replay.io lets you click an event row to jump there, pins comments to execution points, and puts the paused point in shared URLs ([Replay docs](https://docs.replay.io/reference-guide/debugging/commenting)). Google Earth's historical slider has a notch per available image and switches off 3D buildings when historical imagery is on, disabling a feature that cannot be shown as of that time rather than showing it wrongly ([Google Earth developer docs](https://developers.google.com/maps/documentation/earth/historical-imagery)); the workpaper should do the same for actions that did not yet exist at the chosen point. Grafana keeps the time position in the URL ([Grafana docs](https://grafana.com/docs/grafana/latest/visualizations/dashboards/use-dashboards/)), but its core moved to AGPLv3 in 2021 ([Grafana blog](https://grafana.com/blog/2021/04/20/grafana-loki-tempo-relicensing-to-agplv3)), so borrow the interaction, not the code. For showing change between two points, Excel's Show Changes pane gives the previous value per cell ([Microsoft Support](https://support.microsoft.com/en-us/office/show-changes-that-were-made-in-a-workbook-978ceea7-bbf6-4337-bca7-22e7cc9892e8)), which maps directly onto a workpaper line, while Notion's admission that "highlights don't capture every change" ([Notion Help](https://www.notion.com/help/duplicate-delete-and-restore-content)) argues for stating plainly what any diff covers.

The control itself should be a select or listbox of named events plus a separate "Move clock" button, not a slider. The W3C ARIA pattern warns that "some touch-based assistive technology users may have difficulty with slider widgets" ([W3C ARIA APG Slider](https://www.w3.org/WAI/ARIA/apg/patterns/slider/)), and USWDS recommends a select for about 7 to 15 options and warns against auto-submitting on change ([USWDS select](https://designsystem.digital.gov/components/select/)); beyond about 15 events, a filterable combo box is the better fit. Discrete stops also avoid landing between events where no state is defined. The one place the workpaper departs from every precedent is sharing: every surveyed document tool keeps history browsing per user, and only a restore changes shared state, which Notion warns "may affect existing views and how other people see it" ([Notion Help](https://www.notion.com/help/duplicate-delete-and-restore-content)). A shared clock that one person moves for everyone is unprecedented in this survey, so the banner should name who moved it and when, in MediaWiki's format, for example "Viewing the workspace as of *Corrected 1099 received*, 12 Mar 2026, moved by Dana. View only. [Return to latest]." Nielsen's "user control and freedom" heuristic calls for exactly that clearly marked exit ([UX Collective on heuristic #3](https://uxdesign.cc/jakob-nielsens-third-usability-heuristic-for-user-interface-design-de788590665f)). No published usability study on shared, workspace-wide time position was found, so this risk is inferred from product behaviour rather than measured.

## Conclusion

The research shifts the question from "which temporal system should we use" to "which guarantees must the app state out loud." The storage half is solved and small: a sequence-keyed append-only table with database-enforced immutability, a half-open lookup over three `computed_at` values, and live replay. What distinguishes a defensible workpaper is that its time model is the tax domain's own model, which makes it explainable to a tax reviewer without any database vocabulary: acceptance is the documentation completion date, an amendment is a 1040-X delta with a mandatory reason, "as filed" is the return transcript, and "as now known" is the account transcript. That framing is also the best answer to Fowler's warning about user education, because preparers already think in those terms.

The two places where the design goes beyond precedent deserve explicit testing and explicit mention in the hand-in. The shared clock has no surveyed equivalent, so its banner, its "who moved it" attribution and its one-click return to latest are the mitigation, not decoration. And the "current logic over past data" trap, rendering an old moment with the newest return version, is the most likely silent bug in this architecture; it should carry its own automated test alongside the packet-mistake tests, since a past view that quietly shows today's numbers would undermine the very traceability the workpaper exists to provide.
